## 3. Design

### 3.1 Shared shape

Every tool takes `memoryId` (uuid) and `memoryVersion` (`isoDate`, described "ISO-8601 timestamp exactly as get_memory returned it" [C11]); every MCP schema is `.strict()`, including nested `changes` [C11]. Inside one `$transaction(…, TX_OPTIONS)`: `lockMemory` [C22] → read the memory (`deletedAt`, `updatedAt`, `consentVersion`, `contributorNote`, `type`, `status`, `visibility`); missing or `deletedAt` set → `not_found` → `previous = updatedAt`; `previous.toISOString() !== memoryVersion` → `{ code: "stale", current }` → per-tool checks (D11) → write → `recomputeMemoryType` (remove/restore only) [C3] → `appendRevision(tx, { changedVia: "ADMIN", … })` [C3] → `touchMemory(tx, memoryId, previous)` (last Memory write, D2) → `current`. Revision JSON holds ISO strings, never `Date` objects (as `set_deleted` does).

`current` (success, `stale` and `mismatch` answers), built by `mediaEditableView(db, memoryId)` in `features/admin/media-editable.ts` (accepts the transaction client or `getDb()`):
```
{ memoryVersion, status, visibility,
  media:        [{ id, status, mimeType, originalFilename, caption, approxDateText, place, sortOrder }],   // visibleMediaIds rows, LIVE_MEDIA_ORDER
  removedMedia: [{ id, mimeType, originalFilename, caption, approxDateText, removedAt, restorableUntil }] } // the D7 restorable set
```

Stale rule (tool descriptions + SKILL.md, modelled on update_memory's [C17]): on `stale`, compare `status`, `visibility` and every field of every file in `current.media` and `current.removedMedia` with what you read (from `get_memory`, or the `current` of your previous write). If anything differs, show Rob and ask. If nothing differs (only the version moved), retry **once** with `current.memoryVersion`; a second `stale` → stop and tell Rob.

Locking boundary (Oscar O11): the new tools take only `lockMemory` (no upload lease, no budget lock), so the repo's lock order lease → memory → contributor → budget [C22] is untouched; restore needs no budget lock because `storedBytes` counts every READY row whether removed or not [C25]. Writers that do not take the memory lock (cron (a), (f2), GPS, hash, derive, posters) never write a READY row's `caption`, `approxDateText`, `place`, `sortOrder`, `deletedAt` or `purgeAfter`; the replacement swap in ingest does take `lockMemory` [C23].

### 3.2 `update_media`

- Input: `{ memoryId, memoryVersion, mediaId, changes }`; `changes` = `z.object(mediaWordsFields).strict()` [C12] with at least one key (`mediaWordsFields` is a field map, not a schema).
- Target: `id = mediaId`, same memory, `deletedAt` NULL, `replacesMediaId` NULL, `purgedAt` NULL, `status` READY (D10). Otherwise `not_found`.
- Writes only keys that differ; copies them to the target's PENDING replacements (claim.ts does the same [C6]).
- Revision: `before { mediaId, <changed keys> }` → `after { mediaId, <changed keys> }`.
- Returns `{ written: string[], current }`. Refusals: `invalid`, `not_found`, `stale`.
- Annotations: `destructiveHint: true` (overwrites words), `idempotentHint: true` [C14].
- Description: READY files only; for a file still uploading, call `request_upload` again with the words; an APPROVED + PUBLIC memory shows the new words on See memories at once (D4).

### 3.3 `set_media_deleted`

- Input: `{ memoryId, memoryVersion, mediaId, deleted: boolean }`.
- Target lookup: `id = mediaId`, same memory, `replacesMediaId` NULL (removed or not). Otherwise `not_found` (a pending replacement is never a target).
- **Remove** (`deleted: true`):
  - Already removed → `{ changed: false, current }`, plus `restorableUntil` when that file is in the D7 restorable set (George G9).
  - `last_file` when the target is READY, the memory has no words, and it is the last READY non-purged live file (claim.ts rule [C7] plus update_memory's `purgedAt: null` filter).
  - READY → `deletedAt = now`, `purgeAfter = now + 30 d`. PENDING / FAILED → `deletedAt = now` only (a cancellation, D6).
  - Cancel the target's PENDING replacements: `deletedAt = now` only [C7].
  - `recomputeMemoryType`. Revision `before { mediaIds, type }` → `after { mediaIds, type, removedMediaId, purgeAfter (ISO or null), cancelledReplacementIds? }`.
  - Returns `{ changed: true, current, restorableUntil? }` (`restorableUntil` only for a READY file).
- **Restore** (`deleted: false`):
  - Not removed → `{ changed: false, current }`.
  - Not in the D7 restorable set → `not_restorable`.
  - Live READY/PENDING files ≥ `MAX_FILES_PER_MEMORY` → `too_many_files` (the cap's own count [C21]).
  - Clear `deletedAt` and `purgeAfter`; keep `sortOrder` (D9); `recomputeMemoryType`. Revision `before { mediaIds, type }` → `after { mediaIds, type, restoredMediaId }`. A cancelled replacement stays cancelled.
- Refusals: `invalid`, `not_found`, `stale`, `last_file`, `not_restorable`, `too_many_files`.
- Annotations: `destructiveHint: true`, `idempotentHint: true`.
- Description: a removed photo leaves See memories and the sender's claim page at once; a READY file can be restored for 30 days; removing one half of a Live Photo (HEIC + MOV are two unlinked rows) removes only that row; a restored file keeps its old place, so check `current` and use `reorder_media` if needed.

### 3.4 `reorder_media`

- Input: `{ memoryId, memoryVersion, mediaIds: uuid[] }` (1–100, no duplicates; D8).
- Not exactly the visible set → `{ code: "mismatch", current }`. Same order → `{ changed: false, current }`: the no-op compares the **id order** with `visibleMediaIds` (`snapshotsEqual` on the lists), never `sortOrder === index` (after a removal the slots are 0,1,3,4; George G3).
- Write `sortOrder = index` for each, and the same value on its PENDING replacements (D8). Revision `before { mediaIds: old }` → `after { mediaIds: new }`.
- Returns `{ changed, current }`. Refusals: `invalid`, `not_found`, `stale`, `mismatch`.
- Annotations: `destructiveHint: true`, `idempotentHint: true`.
- Description: pass every id in `current.media` (or `get_memory`'s `media` rows whose `replacesMediaId` is null), FAILED rows included; the card on See memories shows the first playable photo in this order [C26].

### 3.5 Cron step (f): the grace

In `app/api/cron/reconcile-uploads/route.ts` [C9], step (f) gets helpers next to `uploadWindowClosed`: `purgeDue(row, now)` (`purgeAfter === null || purgeAfter < now`) and `purgeDueWhere(now)` (`{ OR: [{ purgeAfter: null }, { purgeAfter: { lt: new Date(now) } }] }`).
- Discovery: the removed-file branch becomes `{ deletedAt: { not: null }, AND: [uploadWindowClosedWhere(now), purgeDueWhere(now)] }`. **Trap:** both helpers return an `OR` key, so spreading them into one object would silently drop the window condition; use `AND`. Filtering at discovery also keeps graced rows out of the `take: 50` batch.
- Locked re-check: select `purgeAfter`; `fileRemoved = fresh.deletedAt !== null && uploadWindowClosed(fresh, now) && purgeDue(fresh, now)`. Phase 1 stays under `lockMemory`, so a restore that commits first makes the row ineligible, and a claim that commits first makes the restore `not_restorable`.
- (f2) and (a) are unchanged: they act on PENDING rows only, which never carry `purgeAfter` (D6).
- The deleted-memory branch is unchanged: a memory deleted for 30 days takes its graced files with it.

### 3.6 `get_memory`

- `media[]` gains `replacesMediaId` (null for an ordinary file), so the caller can tell the reorderable set (Oscar O8). The admin page's view type gains it too (no UI change).
- New `removedMedia` = `mediaEditableView(...).removedMedia`, read with a **separate query**; the `media` include keeps `where: { deletedAt: null }`, so `reviewVersionOf(memory)` [C20] sees exactly what it sees today.
- Description mentions both fields.

### 3.7 Accepted side effects

- A removed READY file keeps counting toward `storedBytes` (and its derived copies toward `derivedBytes`) until it is purged, up to 30 days [C25]: it holds room under both the daily budget and `TOTAL_BYTE_CEILING` (default 50 GiB) [C25]. Removing files does not free room for new uploads until the purge.
- `serveMedia` 404s removed files for every caller, admin included: a removed photo cannot be previewed until restored.
- Any MCP photo write makes an open admin edit form or a prior `get_memory` stale (by design; D2).
- A restore may change the card's cover photo (D9).

## 9. Non-goals (what this PR does not do, and why)

- **Routing uploads through jowray.com (Rob's ruling R3).** A Vercel Function cannot carry the bytes because of the 4.5 MB request-body cap [C18]. Only a CDN external rewrite could, and that is untested against vercel.com/api/blob, is cut off at 120 s [C19] (a 500 MB video needs more than 4 MB/s), and would put the presigned URL's signature in Vercel request logs. It also does not help a sandbox that blocks www.jowray.com too. Uploads stay on vercel.com; issue #81 tracks the allowed-domains gap.
- **Admin-page buttons for remove, restore, caption and reorder.** This PR adds MCP tools only. Issue #75 covers admin attach/share buttons; the file-edit buttons are follow-up F-UI.
- **Recording `changedVia: "MCP"`.** Every MCP write records ADMIN today (debt M-E-03). Fixing that is follow-up F-MCP-VIA, not part of this PR.
- **Linking Live Photo pairs.** Issue #86 covers it. Removing one half of a pair removes only that row.
- **Reopening review on admin edits (decision D4).** Like `update_memory`, an MCP file edit keeps an APPROVED memory APPROVED. Only the sender's own claim-page edits reopen review.
- **A dedicated version counter, or making every writer of `Memory.updatedAt` monotonic (Oscar O4, part).** `memoryVersion` is compared for equality only. Only the three new tools and the two claim-page file writers go through `touchMemory`'s +1 ms rule; the other writers (`update_memory`, `set_coordinates`, `share_draft`, upload lease) keep Prisma's automatic timestamp. A collision needs a second writer on a skewed clock landing on exactly the previous millisecond, and changing those tools' contracts is out of proportion to that. Tracked as follow-up F-VERSION (Low).
- **Moving `memoryVersion` when a file is reserved (Oscar O2, part).** Reserving a file via `request_upload` or a claim-page ticket creates a PENDING file and changes no existing file's words. `reorder_media` refuses with `mismatch` (and the current list) when the set of files moved. A PENDING file becoming READY already moves the version through `recomputeMemoryType` (`features/memories/ingest-upload.ts` transition, then `features/memories/media-state.ts:50`).
- **Editing a PENDING file's words through `update_media` (Oscar O2).** A `request_upload` retry rewrites a PENDING row's words from its own arguments, to null when omitted (`features/admin/attach-media.ts:98`; `features/memories/create-memory.ts:68–70`), so an edit there would be silently undone. `update_media` takes READY files only, like the claim page (`features/memories/claim.ts:442` onward). For a file still uploading, call `request_upload` again with the words.
- **Restoring a cancelled upload (PENDING/FAILED) or a cancelled replacement (Oscar O1, O3, O6).** Only a removed READY file keeps its bytes and can be restored. Removing a PENDING/FAILED file is a cancellation with today's purge; cron steps (a) and (f2) handle PENDING rows without the memory lock (`app/api/cron/reconcile-uploads/route.ts:274`, `:663`). A reservation's upload window has usually closed anyway.
- **Version checks on claim-page saves (Oscar O5).** The claim page sends all three word fields with no version (`app/m/[claimToken]/media-list-client.tsx:107–119`), so a stale claim form can overwrite an MCP edit. This is existing last-writer-wins behaviour, the same as for memory-level edits. `touchMemory` only covers the other direction, where MCP sees a claim edit as stale. Tracked as follow-up F-CLAIM-VERSION (Medium).
- **Answering `not_found` when removing a file the sender already removed (George G9, part).** `set_media_deleted deleted:true` on any already-removed file answers `changed: false`: the file is already not visible, which is what the caller asked for. `not_found` would suggest a wrong id.
- **Raw-SQL batching of `reorder_media`'s writes (TCR round 1, Oscar #5).** The reorder reads replacements once and writes only rows whose slot changes; real lists are about a dozen files; the 100-row worst case is proven on Postgres inside the 10 s timeout; raw SQL would bypass Prisma's typing and the automatic `Media.updatedAt` that feeds `reviewVersion`.
- **An activation gate in code for the first deploy (TCR round 1, Oscar #4).** The window is one-time and at most the cron's 60 s `maxDuration`; the S15 prerequisite (wait for a cron run started on the new deployment) covers it, later deploys carry the grace-aware cron, and a rollback restores graced files first (§7).
- **`IF NOT EXISTS` on the migration's CHECK (TCR round 1 research note).** The script runs as one transaction, so a partial apply cannot happen; recovery is in the migration header, as in the `gps_scan_complete` precedent.
- **Extra smoke mutations on Nancy's memory (Oscar O19, part).** Rob's ruling R1 limits the production smoke to the two real fixes plus one no-op reorder. Restore and a real reorder are proven by integration tests, not on a family memory.
