# Draft a memory of Jo on someone's behalf

Condolence notes arrive in Rob's Gmail with real memories of Jo inside them. This skill saves the sender's words as a **DRAFT** memory on jowray.com (invisible and silent until the sender presses **Share this memory** on their claim page) and drafts the reply Rob sends from Gmail with the claim link. The site never emails the sender; Rob's reply is the only message they get.

Design and rulings: `docs/plans/2026-11-03-draft-memory-on-behalf.md` (the feature), `docs/plans/2026-11-05-draft-skill-rewrite-prompts.md` (verbatim-or-rewrite choice, prompts, `originalNote`) and `docs/plans/2026-11-06-mcp-endpoint.md` (the connector and coordinates) in the repo.

## Prerequisites

- **The jowray connector** (the custom connector at `https://www.jowray.com/api/mcp`; setup in `docs/environment.md`, "MCP connector"): `list_memories`, `get_memory`, `draft_memory`, `set_coordinates`, `reissue_claim_link`, `update_memory` for the 409 fixes in step 3, and `suggest_places` for place names from a memory's photos ("Place suggestions from photos" below). It works from any Claude surface. Six tools are set to ask Rob before they run: `draft_memory` and the five destructive ones (`set_coordinates`, `update_memory`, `set_status`, `set_deleted`, `reissue_claim_link`). `suggest_places` only reads, so it runs without a prompt; what it suggests is saved only through `update_memory` or `set_coordinates`, after Rob's answer. So the client shows Rob an approval prompt before each `draft_memory` call too, and step 2b still comes first: an approval prompt is not Rob's answer to a step 2b question, and answering a question is not approval of a tool call. Never call `draft_memory` before step 2b's questions are answered, whether or not this session prompts for it.
- **Fallback, only when no jowray tools are listed at all** (the connector is not added to this session): on Rob's Mac, run the Preflight and step 3's script path; anywhere else, stop and tell Rob the jowray connector is missing. Tools that are listed but fail are a different case (step 3, "Connector errors"). The fallback needs the repo at `/Users/rob/Documents/active_work/jowray_com` with `node_modules` installed (Node 20+), and its `.env` holding `ADMIN_API_SECRET` (never print it). Real runs pass `--prod`; a local test sets `ADMIN_API_URL=http://localhost:3000` instead. There is no default target. This path takes the same JSON (coordinates included) but runs only on Rob's Mac.
- The Gmail connector (`get_thread`, `search_threads`, `list_drafts`, `get_draft`, `create_draft`, `update_draft`). Check which mailbox it is (`authuser=` in any `viewUrl`): the condolence notes may live in a different account from the one this session is connected to.
- Rewrites need the production site to be at or past the merge of the 2026-11-05 plan's PR: `draft_memory` then answers `originalNoteRecorded: true` after a rewrite (the script prints `originalNote: recorded`). Until it does, save verbatim only.

## Hard rules

- **Their words, their choice.** Each memory is saved either as a verbatim copy of the sender's paragraphs about Jo or as a light rewrite that Rob picks and approves, text in hand, before anything is saved. A rewrite is as light and surgical as the note allows (step 2); when the approved text differs from the verbatim cut, the cut is sent as `originalNote` so it sits in the memory's history. Text that ends up identical to the cut is a verbatim save, whatever path led there (the API refuses an `originalNote` equal to `note`). Never save text Rob has not seen.
- **Only an answered question authorises a save.** A question that was cancelled, timed out, closed with partial selections, or answered in chat with an instruction rather than a choice does not authorise anything. PUBLIC being the API default is not a visibility choice. Re-ask.
- **Rob's typed text is either a replacement or an instruction.** Text that reads as the memory itself ("Jo always stopped…") is the approved note. Text that reads as a direction ("use the rewrite but keep 'Dad'") is an instruction: produce a revised proposal and ask again. Newly generated wording always goes back through step 2b.
- **Never tell the sender the words are exactly theirs when they were rewritten.** The reply says what was done (step 4).
- **A `duplicate` (the script's 409) means nothing from this attempt was saved.** Not the words, not the visibility, not the details, not the coordinates. Never describe them as saved, never write a reply that assumes them, never change `sourceInput` to get past the duplicate. Resume from the existing draft (step 3).
- **A rewrite that was sent but not recorded is a defect, not a success.** After a successful save of a payload that carried `originalNote`, `draft_memory` must answer `originalNoteRecorded: true` (the script must print `originalNote: recorded`). `false`, `NOT recorded`, or no `originalNote:` line at all, means production is older than this skill: stop, tell Rob the row holds only the rewrite and the sender's words survive only in the source message, and leave the fix to Rob (step 3's 409 branch shows how to put the verbatim words back). Draft no reply; the claim link is live but stays unsent. A verbatim save answers `false` (prints `NOT recorded` or nothing), which is correct. A `duplicate` carries no such field and follows the duplicate rule instead.
- **Email required.** A note with no sender email is not drafted until Rob supplies one.
- **Reply to the sender only.** `to` is the sender's address; `cc` stays empty. Never reply-all.
- **Nobody presses Share.** Only the sender does, on their own claim page. Never open a real person's claim link to "check".
- **No phone numbers, no street or unit details** in the relationship field or the reply (the field is PUBLIC by default).
- **Coordinates pin a place, never a home.** Only for a named place: a town, a facility or community campus (Broadmead is a place), a church, a park, a lake. Never a residence, a street address or a unit inside a place ("her apartment at Broadmead" gets none), and a phrase that names a home gets none even for its town or campus. Never saved without Rob's answer to the Coordinates question. A photo's `coordinates` from `suggest_places` are where the camera was (often a home) and are never proposed or saved as a memory's coordinates.
- **Reissue is revocation.** A second claim link for the same draft kills the one already sent. Only on Rob's explicit say-so, and only after step 3's Gmail check below.
- **Rob never presses Share, and never edits a draft on its page.** The only button on a draft's page is Share, and Share is the sender's consent. If Rob opens the link to add an attachment, he uses the file control only and closes the tab; a typo is fixed on the admin page or by telling the sender. A `consentedAt` earlier than the time Rob sent the reply means Rob pressed it: flag it.

## Who's who

From the obituary (`app/obituary/page.tsx`): Jo is the person being remembered, Rob's mother. **Richard** Wray is her husband ("Dad" in the notes). **Rob** (Robert) is her son. **Tracy** Gold is Rob's wife. Richard, Rob and Tracy are the family admins.

Resolve every pronoun from *this* message. In a letter addressed to Rob, "your mom" is Jo, "your dad" is Richard, "your parents" and "your mom and dad" are Jo and Richard, and "you" is Rob: these need no question. "You both", "you two", "the family" and any "your …" in a note not addressed to Rob are open until the sentence settles them: leave the words unchanged in the rewrite and ask Rob in step 2b. A pronoun inside a sentence the cut drops needs no question. Never substitute a name the message does not support.

## Procedure

Run the Preflight (above) first, and note which mailbox the Gmail connector is on.

**Resuming after a dead session:** run this check once step 1 has the message id, before step 2: does **this message** already have a row? A row from the same sender may be a different note. For a Gmail note the row's `sourceRef` is `gmail:` followed by the sender's message id in lower case (the server's `gmailSourceRef` lower-cases the 8 to 32 hex characters; the id itself only ever goes in `sourceInput.messageId`). `list_memories(q: "<sender email>")` lists the sender's rows but not their `sourceRef`, so read each candidate with `get_memory` and compare its `sourceRef` (fallback: Rob looks on the admin page). A row with that `sourceRef` means the earlier save landed: continue through the duplicate branch of step 3 with its `memoryId`. No such row means this is a new note: go on to step 2. A text or pasted note's `sourceRef` is a hash the skill never computes, so for those go on to step 2: step 3's save answers `duplicate` if the earlier one landed. Rob's earlier answers still count when he repeats them in chat ("rewrite and FAMILY, nothing else" settles Words and Visibility and leaves When, Where, Coordinates and Relationship blank), but a regenerated rewrite is new wording and still needs his yes on the shown text.

### 1. Resolve the source

**Gmail popout URL with `thread-f:<decimal>`** → convert to the hex thread id and read the thread:

```bash
printf '%x\n' <decimal>
```

`get_thread(threadId: "<hex>", messageFormat: "PLAIN_TEXT")`. Pick the **sender's** message (not Rob's). Keep **that message's `id`** (not the thread id): it goes in `sourceInput.messageId` in step 3, and the server derives the `sourceRef` from it.

**`thread-a:r…` URLs cannot be converted.** Use `search_threads` with the sender and subject Rob gives (for example `from:someone@example.com subject:(Jo)`); if nothing matches, ask Rob to paste the message.

**Pasted text or a text message** → use it as given. Ask for the sender's name and email if missing (email is required). For a text message also ask for the number (E.164) and the time on the message (ISO-8601 with a zone; the dedup key uses that minute), which only ever appear hashed.

Note whether the message has attachments: the skill cannot download them. The reply invites the sender to add the photo on their own page (step 4); Rob does not add it for them (hard rule above).

### 2. Propose the text

Show Rob, in this order:

1. **The verbatim cut**, in a fenced block: the sender's paragraphs about Jo, exactly as written, whole paragraphs only. The cut drops whole lines or paragraphs that hold no memory: greetings and sign-offs ("Dear Rob,", "With love, Pat"), signatures and "Sent from my iPhone", quoted earlier mail (`>` lines), logistics and Dad's health, and standalone condolence lines ("Thinking of you both at this hard time."). A condolence or direct-address sentence that sits **inside** a paragraph about Jo stays in the cut: removing it is a rewrite (step 2.2), never part of the cut. Everything kept is verbatim: no word changes, no partial paragraphs. The **one** normalisation allowed: join lines that a mail client hard-wrapped inside a paragraph; keep the blank-line paragraph breaks. This block is what the sender will see if Rob chooses verbatim, line breaks included, and it is what `originalNote` carries when Rob chooses a rewrite. When the cut itself names a street, unit or phone number, say so under it: the note is PUBLIC by default, and Rob may answer the Words question with a replacement or choose FAMILY.
2. **A light rewrite**, in a second fenced block, **only when the cut still addresses the family rather than speaking about Jo** ("your mom", "you", "your dad") or carries a condolence or direct-address sentence inside a memory paragraph ("I was so sorry to hear about your mom."), followed by a one-line change list measured against the cut ("dropped 'I was so sorry to hear about your mom.'; your mom → Jo ×2; 'you' → 'Rob'"). A light rewrite is the cut's own sentences, order, tense, vocabulary and paragraph breaks, with only the changes needed for the memory to make sense on a shared family website: whole sentences addressed to the family that hold no memory are dropped and listed; addressee references become the person's name as the message establishes it (Who's who); pronouns are fixed only where a change requires it. No new facts, no added adjectives, no summarising, no reordering, no smoothing of style; typos stay unless they obscure meaning. If a pronoun's referent is unclear, leave it unchanged and list it as an open question. If the cut already reads as a memory about Jo, say so and show no rewrite.
3. **Sender name and email.** The **relationship**: "stated" with the phrase it comes from, or "inferred" with the reason ("Neighbor", from 'when she walked past my feeder'), with no street or unit details ("Neighbor at Broadmead", "Friend from Ticonderoga Methodist"). Proposed **roughly when** and **where**, each with the phrase in the note it comes from, or "not stated". A time phrase is proposable only when it names a period a reader can place ("Summer 1998", "every Fourth of July", "the winter she retired"); a bare season or "years ago" is "not stated". A place is proposable when it names somewhere ("the lake", "Broadmead", "her kitchen"); a street or unit is never proposed.
   Then **coordinates** for that place, only when it is a named place a map can find (a town, a facility or community campus such as Broadmead in Cockeysville, a church, a park, a lake): WGS 84 decimal latitude and longitude of the place itself, with the phrase they come from and where the numbers come from (a map or web search result; never guessed). "Her kitchen", "the lake" with no name, a street address, a home, or a unit inside a place ("her apartment at Broadmead") get **no coordinates**: say why in one line (they would pin a home, or there is nothing to look up). When the place phrase names a home ("12 Elm Road, Towson", "her apartment at Broadmead"), propose no coordinates at all, not even for the town or campus it sits in. When no map or search tool is available to look the place up, propose none and say so: never guess the numbers.
4. Whether the message has an **attachment**.

### 2b. Ask Rob

Questions, in this priority order; each call holds at most four questions and every question has two to four options, so the overflow goes into a second call right after the first. Headers are at most 12 characters: `Words`, `Visibility`, `Pronoun`, `When`, `Where`, `Coordinates`, `Relationship`, `Name`. If no question tool is available, ask the same questions in one chat message and wait for choices. Skip any question Rob already answered in chat for this memory; a selection a timed-out dialog submitted is not an answer.

1. **Words** (always). Options: "Verbatim copy"; then "Light rewrite (as shown)" when step 2 showed one, otherwise "Propose a light rewrite". Choosing "Propose a light rewrite" runs step 2 again with a rewrite and then step 2b again for Words and any Pronoun question before anything else happens. Rob's own text arrives through the free-text row: apply the replacement-or-instruction hard rule.
2. **Visibility** (always). Options, from `lib/visibility.ts`: "Everyone who visits jowray.com (PUBLIC, default)" / "The whole family (FAMILY)" / "Richard, Rob and Tracy only (PRIVATE)".
3. **Pronoun** (one per open referent, only when step 2 showed a rewrite): the sentence quoted, at most three Who's who candidates as options, plus "Keep as written". Rob's answer is what supports the name; the free-text row does not count toward the two-to-four options. Pronoun answers apply to the rewrite only: when Words is "Verbatim copy" they are ignored, and an unanswered Pronoun question does not block a verbatim save.
4. **When.** Options: the proposed value when step 2 proposed one; always "Leave blank (the sender can fill it in)"; and "Ask the sender in the reply" (adds one line in step 4).
5. **Where.** Same three shapes.
6. **Coordinates** (only when step 2 proposed them). Options: the proposed pair with the place, as `<latitude>, <longitude> (<place>)`, and "Leave blank". Coordinates are sent only when Rob picks the pair **and** keeps the proposed Where (the two may sit in the same call); "Leave blank", a skipped question or any other Where answer sends none.
7. **Relationship** (whenever step 2 proposed one, stated or inferred). Options: the proposed wording and "Leave blank", with "Leave blank" first when it was inferred. When step 2 proposed nothing, omit `relationship` without asking.
8. **Name** (only when the signature and the From line disagree): the two readings as options. When no name is known at all there is nothing to offer: ask Rob in chat, as step 1 does.

Then, before step 3: if Rob typed his own text and it differs from the block he was shown, or a pronoun answer changed the rewrite, show the final text once more in a fenced block and get a plain yes. Typed text identical to the shown rewrite needs no second yes.

### 3. Save the draft

Build the input. Describe **where the words came from** in `sourceInput`; the server derives `source` and `sourceRef` through the canonical builders in `lib/source-ref.ts`. Never compute a `sourceRef` by hand, and never send `source` or `sourceRef` (`draft_memory` refuses them).

```json
{
  "contributor": { "name": "<name>", "email": "<email>", "relationship": "<relationship or omit>" },
  "note": "<the approved text: the verbatim cut, or the rewrite as Rob approved or edited it>",
  "originalNote": "<the verbatim cut; include ONLY when note differs from it>",
  "approxDateText": "<or omit>",
  "place": "<or omit>",
  "visibility": "<PUBLIC | FAMILY | PRIVATE, as Rob chose>",
  "coordinates": { "latitude": <number>, "longitude": <number> },
  "sourceInput": { "kind": "gmail", "messageId": "<the sender's message id>" }
}
```

Omit `originalNote` whenever the approved `note` equals the verbatim cut, however Rob arrived there (a "Keep as written" answer or an instruction can undo every change): that is a verbatim save, and the server refuses (`invalid`, the script's 400) an `originalNote` equal to `note`. Omit `relationship`, `approxDateText` and `place` when Rob chose "Leave blank" or "Ask the sender in the reply", or when nothing was proposed. Include `coordinates` **only** when Rob chose the proposed pair (step 2b, Coordinates), as two numbers (not strings) exactly as he saw them; otherwise leave the key out.

`sourceInput` is one of:
- `{ "kind": "gmail", "messageId": "<sender's message id>" }` → `source: EMAIL`.
- `{ "kind": "sms", "number": "<E.164>", "sentAt": "<ISO-8601 with an explicit zone, e.g. 2026-11-03T14:05-05:00>", "text": "<the full text message>" }` → `source: SMS`. The zone is required (a zone-less time would hash differently on another machine). Keyed on number, the minute (UTC) and the text, so a retyped zone or seconds cannot make a second draft and two texts in one minute stay distinct.
- `{ "kind": "other", "originalText": "<the whole original message, not the excerpt>" }` → `source: OTHER`. The dedup key uses `contributor.email`; an `email` field here must match it.

**With the connector:** call `draft_memory` with this object. A success answers `{ memoryId, claimLink, originalNoteRecorded }`; check `originalNoteRecorded` against what was sent: a rewrite must answer `true` (hard rule above), a verbatim save `false`. A refusal answers `isError` with a `code`: `duplicate` (`memoryId`, `status`) is the 409 branch below, `invalid` (`message`) is the 400, `budget_exceeded` is the 429. `internal` (`eventId`) means the server failed: tell Rob the `eventId` (it is in Sentry); one retry of the same call is safe, because a call that did commit answers `duplicate` on the retry. A call that times out or returns nothing is retried once the same way, with the identical arguments (never alter `sourceInput` or anything else); a `duplicate` on that retry is the lost-response case below. The script fallback follows the same rule: one re-run with the identical file, and a 409 on it is that same case.

**Script fallback** (no connector): write the object to a JSON file in the scratchpad (never in the repo) and run the script from the checkout, which prints the host it is about to call, then `memoryId`, `claimLink` and, when the server knows the field, `originalNote: recorded` or `originalNote: NOT recorded`. Always `cd` into the checkout in the same command: the script's `@/` imports resolve only with the checkout as the working directory, so an absolute script path run from anywhere else fails with `MODULE_NOT_FOUND` before any request. A reissue (`--prod --reissue <memoryId>`) runs the same way.

```bash
cd /Users/rob/Documents/active_work/jowray_com && npx tsx --env-file=.env scripts/draft-memory.ts --prod --input <absolute path of the json-file>
```

Delete the JSON file once the script has answered (a `memoryId` or a refusal); after a timeout or no output, keep it for the one re-run. Check the `originalNote:` line against what was sent: a rewrite must print `recorded` (hard rule above); a verbatim save prints `NOT recorded` or nothing. The script's 409, 400 and 429 are the `duplicate`, `invalid` and `budget_exceeded` answers below.

- **`duplicate` (409), status DRAFT**: a draft already exists for this message, with its own words, visibility, details and coordinates; **nothing from this attempt was applied**, and a link for it may already be in Gmail. A lost response after `draft_memory` committed (timeout, dead session) shows up as `duplicate` with no link on retry; the recovery below applies: check Gmail, then `reissue_claim_link` on Rob's yes, which is safe because the link was never sent. **First, read the row:** `get_memory(memoryId)` gives its words (`contributorNote`), `visibility`, `place`, `coordinates` and `revisions`, which are the **newest 25 only**, newest first. The draft's **creation revision** is the ADMIN revision whose `after` carries `sourceRef` and `status: "DRAFT"` (only the save that created the draft writes those); never pick it by position, because every later edit, `set_coordinates` included, adds a revision and can push it out of the 25. **If no revision has that shape, the creation revision is outside the window: tell Rob so, and do not classify the draft or propose any `update_memory`**; Rob checks the words himself. Without the connector, Rob reads the same on the admin page (`/admin`, the sender's name; its History reads the same newest 25 revisions but hides coordinates-only ones, so it can show fewer rows than `get_memory`). **For diagnosis, classify from the creation revision, never from the row's current words** (a DRAFT can be edited without Share, by the sender on the claim page or by an admin). The verbatim cut is step 2's first block; a resumed run that came straight here makes it from the source message as step 2.1 describes. Its `after.note` equal to the verbatim cut → a verbatim draft; `after.note` different and `before.note` present → a recorded rewrite; `after.note` different and `before` empty → the unrecorded-rewrite defect. Then compare the row's current `contributorNote` with that `after.note`. If they differ, the words were edited after the save: name who from the newer revisions that touch `contributorNote` (`changedVia: "CLAIM_LINK"` is the sender on the claim page, `"ADMIN"` a family admin), tell Rob, and propose no `update_memory`. This classification only finds the defect; the reply's wording comes from the row's current words (the step 4 bullet below). Only the defect with unedited words is fixed: the words go back to the verbatim paragraph before anything else (a deleted draft keeps its `sourceRef`, so deleting does not allow a redraft), and no reply is drafted until the row is right. With the connector that edit is `update_memory` with `changes: { note: "<the verbatim cut>" }` on Rob's explicit yes (the `update_memory` rule below); otherwise Rob makes it on the admin page. **Then check Gmail before offering anything**, with all three calls whatever the source: `get_thread` on the sender's thread (the `threadId` from step 1; a text or pasted note has none), for a reply Rob already sent there (it omits drafts); `list_drafts(query: "to:<sender email>", view: "DRAFT_VIEW_FULL")`, for an unsent reply and its body; and `search_threads(query: "in:sent to:<sender email> jowray.com/m/")`, for a reply sent outside that thread (it excludes drafts):
  - An unsent Gmail **draft** to the sender **in the sender's thread** with a `/m/` link → the reply for this memory is already drafted and its link is probably live; say so, because the site cannot confirm a link without its token. Show Rob the draft and the `memoryId` from the duplicate answer, tell him the reply is ready to send, and offer no reissue. Reissue only if Rob asks for one himself, and then replace the link in that draft. When the sender's thread holds more than one of their notes, a `/m/` link in a draft there cannot be attributed by thread alone: show Rob the draft and let him say which memory it belongs to, as for a draft outside the thread.
  - A **sent** reply with a `/m/` link, in the sender's thread or found outside it → the person most likely holds a working link. Do not reissue unless Rob says, in so many words, that he wants to revoke it (for example because it leaked or he knows a reissue happened after it was sent).
  - A draft or sent reply **outside the sender's thread** may instead carry the link of another memory from the same sender (a second note). The site cannot tell which: show it to Rob and let him say; never change or reissue on a guess.
  - No draft and no sent reply with a `/m/` link in any of the three calls → the link was lost (a session died, or a response was lost, between the save and the Gmail draft). Offer `reissue_claim_link(memoryId)` (fallback: `--prod --reissue <memoryId>`) and say that any link already sent stops working; here none was sent, so nothing breaks. Only on Rob's explicit yes.
  - After any reissue, put the new link into the Gmail draft that carries this memory's link with `update_draft`, replacing the old `/m/` link, never adding a second; never leave a draft carrying a dead link. A draft or reply Rob says belongs to another memory stays as it is.
  - Rob wants different words, visibility or details than the existing draft has → `update_memory` with only the changed keys, on Rob's explicit yes (fallback: the admin page, `/admin`, "Drafts"); coordinates → `set_coordinates` with the `memoryVersion` from `get_memory`, under the same coordinate rules as a new draft. Each of these two writes answers with the committed `memoryVersion` (`set_coordinates` next to `changed`, `update_memory` inside `current`): pass it to the next write instead of re-reading. `set_coordinates` never changes `contributor.contributorVersion`. `reissue_claim_link` also moves `memoryVersion` but answers without it: after a reissue, re-read with `get_memory` before the next write. Do not try a second draft with an altered `sourceInput`.
  - **The `update_memory` rule.** Read `memoryVersion` and `contributor.contributorVersion` from `get_memory` first (or take `memoryVersion` from the answer of a write you just made) and send them with only the keys Rob asked to change. On `stale`, compare **every** editable field in `current` (`note`, `name`, `relationship`, `approxDateText`, `place`, `visibility`) with the value you read before this edit (from `get_memory`, where `note` is `contributorNote` and `name` and `relationship` sit under `contributor`, or from the `current` of your previous write). If any field differs, someone else changed the row, even when it is a field Rob asked to change (the sender saving new words on the claim page while Rob edits them): show Rob each changed field, as read and as it is now, and ask before retrying; a retry would overwrite their change. Only when no field differs (just the versions moved, for example after a reissue or a coordinates change), re-read with `get_memory` first: if `status` is no longer `DRAFT`, the sender has pressed Share (their consent), so stop and tell Rob, as for a `duplicate` with status PENDING; otherwise retry once with the versions from `current`, without asking.
  - **Any step 4 that follows a duplicate** (with or without a reissue) takes its saved line from the words the sender will see: the row's **current** `contributorNote`, read with `get_memory` after any `update_memory` above. Never from this attempt, and never from the creation-revision classification (a verbatim draft rewritten later by an admin no longer holds the sender's words; a repaired defect does). Current words equal to the verbatim cut → the "in your own words" line. Different, and the sender has not edited the words since the save (no `CLAIM_LINK` revision after the creation revision changes `contributorNote`, that is, its `before` and `after` values differ; a family admin's edit, this run's included, is a trim like the rewrite) → the "trimmed lightly" line. Different and edited by the sender on the claim page since the save, or no way to tell (the creation revision is outside the 25-row window): ask Rob which line fits, or what to say instead, because neither may describe what the sender will now see. A reissue never clears the row check above; it only replaces the link.
- **`duplicate` (409), status PENDING or later**: the person already shared it. Stop; tell Rob.
- **Connector errors** (the jowray tools are listed but calls fail to connect, time out or answer 401, after the one `draft_memory` retry above): the connector's header does not match `MCP_API_SECRET` in production, or the endpoint is down. Stop and tell Rob (`docs/environment.md`, "MCP connector"); on his Mac, offer the script fallback. No jowray tools at all is not this case: that is the fallback in Prerequisites.
- **401** (script): `ADMIN_API_SECRET` is missing locally or differs from Vercel. Stop.

## Place suggestions from photos

The connector has no file upload: photos reach a memory only through the site (the sender, or Rob, adds them on the claim link page or on /share; a draft's reply asks the sender to add the photo). The server reads the GPS saved in each photo's original and keeps it with that photo. Rob's iPhone route: open the memory's claim link in Safari, add the photos from Photos with Location on, then ask Claude "suggest places for memory X".

Once a memory has photos (on Rob's request, or after a duplicate shows the draft has some), call `suggest_places(memoryId)`. It changes nothing and needs no approval. Its answer:

- `photos`: one row per photo whose place names came back, with `mediaId`, `originalFilename`, `coordinates` (where the camera was) and `labels`. A label is `{ text, kind }`: `kind: "town"` (town and region) or `kind: "landmark"` (a named non-residential place, then town and region), and a landmark also carries `point`, the place's own WGS 84 point. `labels: []` means the lookup found nothing worth offering for that photo.
- `pending`: photo ids whose lookup was busy or failed. Call `suggest_places` again at most twice (answers are cached, so the photos already found return at once), then tell Rob which photos are still pending, by `originalFilename`.
- `attribution`: "© OpenStreetMap contributors". Say it under any list of place names you show Rob.
- Nothing in `photos` or `pending`: no photo has a saved location (phones often strip it on upload). Say so; never guess one.
- Refusals: `not_found` (no such memory, or it is deleted), `disabled` (place lookups are off on the site), `daily_limit` (the site's daily lookup budget is spent; try tomorrow), `provider_refused` (OpenStreetMap refused the site). Tell Rob; do not retry. `internal` (`eventId`) means the server failed: tell Rob the `eventId` (it is in Sentry); one retry is safe, because the tool writes nothing. Calls that fail to connect, time out or answer 401 are step 3's "Connector errors".

Then propose, and **ask Rob first**, with the question tool under step 2b's limits (headers `Where` and `Coordinates`, two to four options each; no question tool: one chat message, then wait):

1. **Where.** Options: up to three distinct label `text`s, those shared by the most photos first, each with the photo it came from, and "Leave as is" (show the memory's current `place` from `get_memory`). A picked label is saved with `update_memory` and `changes: { place: "<label text>" }`, under the `update_memory` rule (step 3). Rob may type his own text instead.
2. **Coordinates**, only when a **landmark** label was offered: options `<latitude>, <longitude> (<label text>)` from that label's `point`, and "Leave blank". Save with `set_coordinates` only when Rob picks the pair **and** the same label as Where, using the `memoryVersion` from the `update_memory` answer (or `get_memory`). A town label carries no point: it gets no coordinates here (step 2's map-lookup rule still applies if Rob asks for them). Never offer a photo's `coordinates`, and the place rule still governs: no home, street or unit, even when a label names a place nearby.

Never put a photo's `coordinates` in a Gmail reply, a report line or anywhere outside this conversation with Rob.

## What the site does with a draft

- `Memory.status = DRAFT`, `consentedAt = null`, `source = EMAIL|SMS|OTHER`, `sourceRef` unique. One Contributor per draft, with `contactOptIn` **off** until the person presses Share (the page prefills both checkboxes on, like /share, and Share records their choice).
- A rewritten draft carries the verbatim excerpt in its creation revision (the ADMIN revision whose `after` has `sourceRef` and `status: "DRAFT"`; `before.note` is the verbatim excerpt, `after.note` the rewrite). `get_memory`'s `revisions` are the newest 25; the admin page's History reads the same 25 and hides the coordinates-only ones among them. So the creation revision is visible only until a memory has had more than 24 later revisions (each edit, status change and `set_coordinates` adds one); after that it is still in the database (`MemoryRevision`) but in neither view. The sender's claim page never shows History. A verbatim draft's creation revision has an empty `before`.
- The claim page shows "A memory of Jo, in your words", the editable fields, the two preference checkboxes and one button, **Share this memory**. Pressing it sets `status = PENDING` and stamps `consentedAt` / `consentVersion`. A repeated press never restamps.
- No site email, before or after Share. The reconcile cron skips these memories, so it never rotates the token behind the link Rob sent.
- Reissue (`reissue_claim_link`, or the script's `--reissue`) is allowed only while DRAFT.
- Coordinates (optional, WGS 84) live only in the database and the connector's answers: the claim page and the admin page never show them, and editing `place` leaves them alone.
- The family-admin alert is not sent for a DRAFT; the cron sends it within ten minutes of the person pressing Share, dated by that moment.
